# Фидбэк: несколько независимых команд на одну сессию и на один воркспейс

**Кому:** мейнтейнеру AgentTeams (NanmiCoder/dsh-agent-teams), issue-draft
**От:** пользователь этой копии (локальный чекаут `87c95c9`, пакет 0.1.20)
**Тема:** `agent_teams_create` отказывает, когда у капитана уже есть команда; одна сессия не может вести N команд; запустить команду в другом воркспейсе можно только из сессии этого воркспейса.

---

## 1. Что нужно

Два требования, оба про **горизонтальное масштабирование**, не про качество отдельной команды:

| # | Требование | Как это выглядит для пользователя |
| --- | --- | --- |
| R1 | **N независимых команд в разных воркспейсах** | `D:\OwlCats\DCB` — команда по материалам, `D:\OwlCats\AI_Tools` — команда по плагину, `D:\OwlCats\DCB-ML` — третья. Все живут одновременно, у каждой своя доска, свой DAG, свои участники, свой бюджет. |
| R2 | **N независимых команд в одном воркспейсе** | В одном репозитории две-три параллельные команды: одна чинит регресс, вторая пишет документацию, третья гоняет верификацию. Не «фазы одной команды», а именно разные команды с разными капитанами и разными целями. |
| R3 | *(следствие)* Одна сессия должна **выбирать**, какой командой работать | Сейчас команда выводится из личности вызывающего (id сессии), поэтому выбор невозможен в принципе — см. §2. |

Текущее поведение в формулировке пользователя: «только одна работающая тима и невозможность поставить новую — это ужасно».

## 2. Почему сейчас нельзя: точные места в коде

### 2.3 Воркспейс команды — это `cwd` сессии капитана

- `src/tools.ts:146-148` — `workspaceOf(agent) = agent.session.header.cwd ?? process.cwd()`

Отсюда жёсткое следствие: **одна сессия физически не может вести команды в разных папках** — `cwd` у сессии один и задаётся при её создании. Для R1 нужны отдельные сессии (или явный `workspace`/`team_id` в аргументах). Для R2 отдельные сессии не нужны — мешает только §2.2.

## 3. Предлагаемый дизайн

Принцип: **личность команды должна быть данными, а не свойством вызывающей сессии.** Сейчас наоборот: `team = f(captain.id)`.

### Фаза 1 — минимум, разблокирующий R1+R2 (без новых ключей конфига)

1. Добавить необязательный `team_id` **всем** team-scoped инструментам; при отсутствии — сохранить текущее поведение «единственная команда капитана» (обратная совместимость).
2. Заменить инвариант «одна команда на капитана» на «одна команда на `(captainSessionId, teamId)`». Уникальность `teamId` внутри `stateRoot` сохраняется (уже есть: `src/tools.ts:781-784`), имена команд остаются человекочитаемыми, id — из имени.
3. `agent_teams_create`: вместо отказа при существующей команде — создавать новую, если имя не занято. Отказ оставить **только** для точного совпадения `teamId` («id taken») и для превышения лимита (новый ключ, см. фазу 3).
4. `agent_teams_status`: возвращать **список** команд капитана (`teams: [{id, name, phase, halted, tasks: {total, done}, members: n}]`), а не одну; при вызове с `team_id` — детально одну.
5. `findTeamByCaptain`/`findTeamByParticipant`: возвращать список; `ambiguous`-ошибка остаётся только там, где инструмент требует ровно одну команду и `team_id` не передан, и её текст должен **перечислять кандидатов и способ выбрать** (сейчас текст не подсказывает, что делать).
6. Веб-роуты `halt`/`plan`: принимать `teamId` из тела (или находить по `teamId` в пределах воркспейса), снимая привязку «одна команда на сессию».

### Фаза 2 — N команд в UI и в планировщике

1. Планировщик: вместо цикла «одна команда капитана» — очередь по всем живым командам всех воркспейсов; кап на команду и глобальный кап (переиспользовать механику PR #144).
2. Панель: переключатель команд (список + вкладка), на каждую — свой DAG, свои участники, свой прогресс. Сейчас `liveCaptainTeam` берёт первую подходящую.
3. Почтовый ящик: маршрутизация по команде (`src/mailbox.ts:58` уже ищет по `findTeamByCaptain` — станет неоднозначной).

### Фаза 3 — лимиты и наблюдаемость

- `maxTeamsPerWorkspace` (по умолчанию, например, 4), `maxTeamsPerSession` (например, 8), `maxConcurrentWorkers` (на команду) и `maxConcurrentWorkersGlobal`.
- В `agent_teams_status` — сводка по всем командам: сколько в работе, сколько задач в очереди, кто держит слот.

### Фаза 4 — настоящее разделение (нужно только для #176)

Вынести личность капитана из `captainSessionId` в отдельную сущность (`captainId` + `attachedSessionIds[]`), чтобы команду можно было продолжить из другой сессии/после форка. Это дороже, и для R1/R2 **не требуется** — но именно это снимет `#176` и «хвосты» вроде «не могу вернуться к команде после перезапуска чата».

**Явно вне области работ:** состояние команды остаётся в воркспейсе (`<workspace>/.agent-teams`), никакого переноса в `~/.dsh`. Иначе ломается вся схема видимости артефактов рядом с репозиторием.

## 4. Критерии приёмки (как проверить, что готово)

1. **R2, функционально:** в одном воркспейсе создаются две команды без ошибок; `agent_teams_status` возвращает обе; задача, созданная в команде B, не появляется в команде A; `update_task(team_id=A)` не может изменить задачу B.
2. **R1, функционально:** две сессии в разных воркспейсах ведут две команды одновременно; участники обеих работают, не блокируя друг друга; «стоп» одной команды не трогает вторую.
3. **Изоляция:** почта, планы, архивы, роут `/state` и снапшоты панели не смешивают команды; `?archived=1` показывает архив каждой команды отдельно.
4. **Обратная совместимость:** существующая одиночная команда продолжает работать без `team_id`; сохранённые `team.json` без новых полей читаются (сейчас в проекте есть культура «cold-resume игнорирует грязные опциональные поля», её надо сохранить).
5. **Планировщик:** при двух командах со свободными задачами и одним свободным участником не происходит двойного назначения; участник не получает две задачи одновременно.
6. **ТDD-скрипты (обязательно, стиль проекта):**
   - `scripts/multi-team-tdd.mjs` — чистые правила: два создания в одном state root, разрешение `team_id`, изоляция `update_task`, форма списка в `status`, лимиты;
   - `scripts/multi-team-panel-tdd.mjs` — проекции фронтенда: выбор команды, отсутствие смешивания DAG, поведение при `halted` одной из двух.
7. **Негативные проверки:** третий `create` с тем же именем → понятная ошибка про занятый id, а не про «уже ведёшь команду»; запрос без `team_id` при двух командах → ошибка со списком кандидатов.

## 5. Риски и что сломается, если сделать наивно

- **Неоднозначность во всех местах, где сейчас один результат:** `src/mailbox.ts:58`, `src/index.ts:269`, `src/index.ts:325`, `src/capabilities.ts:43`. Их надо пройти все, иначе получится «создать две можно, а работать — только одной».
- **Инвариант «одна команда на капитана» — часть протокола в системном промпте** (`src/index.ts:146`, пункты про «Continue existing work», «создавать только когда команды нет»). Требование «создавать новую только по явному запросу пользователя» надо переселить в текст инструмента, иначе капитан начнёт плодить команды сам.
- **Стоимость.** N команд = N параллельных участников. Нужны кап и наблюдение (фаза 3), иначе это превращается в #96 («слишком дорого по токенам») и #117 (утечка памяти при долгих командах).
- **Веб-роуты без авторизации команды.** Ошибка вида «переиспользовать `teamId` из UI без проверки, что запрашивающий — капитан этой команды» даст дыру: чужая команда остановится по чужому запросу. Проверка `requireFreshCaptainTeam` должна сохраниться на всех путях.

## 6. Отношение к R3 (одна сессия, много команд) — честная оценка

R1 и R2 можно закрыть, **не** отвязывая команду от сессии: достаточно `team_id` в инструментах и списка в `status`, а разные воркспейсы обслуживаются разными сессиями (для R1 это неизбежно из-за `cwd`).

Полное «одна сессия рулит любыми командами в любых папках» требует фазы 4 плюс явного `workspace`/`state root` в аргументах, и здесь придётся решать вопрос безопасности: инструмент с произвольным `workspace` — это доступ к состоянию и артефактам любого каталога машины.
