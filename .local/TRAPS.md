## 1. Правка исходников через PowerShell уничтожает UTF-8

**Что случилось.** Дважды: `scripts/lifecycle-verify.mjs` и `.local/t5-replay.mjs`.
`(Get-Content file -Raw) -replace ... | Set-Content -Encoding utf8 file` превратил
кириллицу, длинные тире и рамки комментариев в мохнатую кашу (`â€"`, `Â§`), то
есть файл перестал быть тем, что коммитится. Оба раза пришлось откатывать из
git и накладывать правки заново.

**Почему.** Windows PowerShell 5.1 в этом окружении читает файл как ANSI, если
не указать кодировку явно; `-Encoding utf8` при записи добавляет BOM и не спасает
от уже испорченного чтения. Node-скрипты проекта — UTF-8 без BOM.

**Что делать.** Править исходники только инструментами `read`/`edit`/`write`.
Если очень нужен скрипт — читать и писать через `[System.IO.File]::ReadAllText` /
`WriteAllText` с `New-Object System.Text.UTF8Encoding($false)` **и** предварительно
проверить, что паттерн найден (иначе получите молчаливую запись без изменений).
После любой массовой замены: `Select-String -Pattern "â€|Â"` по файлу — должно
быть 0 совпадений.

**Проверка.** `git diff` по файлу: если в диффе появились строки, которых вы не
меняли (`+// â”€â”€ ...`), файл испорчен — `git checkout -- <file>` и заново.

## 2. Планировщик: свежий attempt участника ≠ потерянный владелец

**Что случилось.** Участник делал `claim_task` → `update_task(in_progress)`, и
фоновый kick планировщика **переклеймивал его же задачу**: attempt 1 → 2, статус
откатывался на `claimed`, следующий `update_task` участника падал либо как
`stale attempt`, либо как `task status cannot move from "claimed" to "completed"`.
Найдено при написании t5-replay; реальный рабочий мог потерять свою задачу.

**Почему.** В `installTeamScheduler` маркер `parkedAttempts` смешивал два
противоположных смысла: «этот attempt мы уже видели» и «владелец потерян».
`update_task` не создаёт новый attempt, поэтому capability участника для
планировщика выглядит как чужой. Плюс `recoverOwned` перекрывал диспатч:
если у участника оставалась открытая задача, `nextReadyTask` вообще не
вызывался, и следующий pending-таск не раздавался никогда.

**Что делать (уже сделано в `0108c81`).**
- `scheduler.noteClaimedAttempt(memberId, attemptId)` — вызывается из
  `claim_task`, чтобы планировщик знал: этот capability наш.
- `recoverOwned` требует, чтобы attempt не был в `knownAttempts`.
- **Порядок выбора задачи: сначала `nextReadyTask`, потом recovery.** Recovery —
  это fallback, а не первый выбор.
- Регрессии: `a member keeps its own in_progress attempt across a scheduler kick`,
  `a member can complete the task it is holding` в `scripts/lifecycle-verify.mjs`.

**Ловушка для S08+.** Любой новый путь, который создаёт/меняет attempt
(`amend_task`, `retry`, `supersede`, `replan`), обязан либо проходить через
`beginTaskAttempt`, либо регистрировать capability через `noteClaimedAttempt`.
Иначе тот же баг вернётся.

## 3. Фоновые kick'и делают состояние команды недетерминированным

**Что случилось.** В t5-replay шаг N+1 читал состояние, которого шаг N не
производил: `update_task` пишет состояние, потом **не ожидая** дёргает
планировщик, и тот продолжает работать параллельно с чтением.

**Что делать.** Для детерминированных сценариев: сигнал, у которого сразу после
вызова делается `abort()`. Запись уже закоммичена, а пост-запись кик
превращается в no-op (`kick` бросает abort, инструмент глотает это как
транзиентный сбой wake-up). В реплеере это хелпер `settle()`.

**Не делать.** Не «лечить» это симметричными sleep'ами: гонка не исчезает, а
тест становится флейки.

## 4. Engine ловушки state machine

- `claimed → completed` **не переход**. Участник обязан отправить `in_progress`,
  потом терминальный статус. Любой скрипт, который «claim → completed», получит
  `task status cannot move from "claimed" to "completed"` — и это не про гейты.
- `failed` / `cancelled` / `completed` — терминальные, попытка что-то записать
  даёт `terminal task ... is immutable`.
- Гейт выполнения проверяется **до** проверки перехода, поэтому ложный `passed`
  против red-замера отвергается как `verify failure must fail the task`, а не
  как неверный переход.
- `waived` требует непустой `evidence` на уровне парсера **и** на уровне
  `team.json`. Пустой waiver ломает всю команду при перечитывании.

## 5. ESM-цикл `state.ts` ↔ `quality-gates.ts`

`state.ts` реэкспортирует чистые функции из `quality-gates.ts`, а
`quality-gates.ts` импортирует `TASK_TRANSITIONS` обратно из `state.ts`. Значения
из такого цикла можно читать **только внутри функций**. Модульная константа
(`const X = TASK_TRANSITIONS`) падает `ReferenceError: Cannot access ... before
initialization`. Вынести таблицу в `quality-gates.ts` тоже нельзя: тогда
`state.ts` пришлось бы импортировать её из модуля, который сам импортирует
`state.ts` за хелперами.

## 6. Прочее, уже подтверждённое

- **BOM.** Windows-редакторы пишут UTF-8 BOM; `JSON.parse` отвечает
  невнятным `Unexpected token`. Любой читатель конфига обязан снимать BOM
  (см. `inspectConfiguredProfiles`).
- **Sandbox.** `pnpm verify` целиком, `compatibility.test.mjs` и
  `harness-runtime-verify.mjs` здесь заблокированы — «left for CI», не
  обходить. `*.test.mjs` запускать как `node <file>`, не `node --test`.
- **Порядок прогона.** Гонять только затронутые сьюты по ходу шага; все 18 +
  `verify.mjs` — один раз перед коммитом. Полный прогон на каждой правке — это
  основные минуты простоя.
