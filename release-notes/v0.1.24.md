# AgentTeams v0.1.24

This release makes **team identity an argument instead of a property of the calling
session**, so one workspace can hold several independent teams. No status, gate rule or
tool name changed; the tool set stays at 18.

- **Every team-scoped tool takes `team_id`.** `agent_teams_create` answers with the id
  (derived from the team name) and you pass it on every later call. The parameter is
  optional *in the argument schema* on purpose: the runtime validates arguments before the
  handler runs, so a schema-level "required" would answer a missing id with a bare
  `missing required property`. Instead the handler answers
  `team_id is required: you participate in 2 teams (multi-a (Multi A), multi-b (Multi B))`,
  which is enough to correct the call in one step. An unknown id names your teams the same
  way. The system prompt now carries the rule: remember the id from the `create` answer, and
  call `agent_teams_status` with no argument when you have forgotten it.
- **A member of exactly one team still omits the id.** The plugin substitutes the only team
  the caller takes part in, so the member prompt and the member tool calls are unchanged.
- **A captain may lead several teams; a second one needs `new_team: true`.** Without the
  flag, `create` answers with the teams you already lead and tells you to continue one of
  them — the historical guidance ("use `agent_teams_status` and continue the existing team,
  do not delete and recreate it") is retained and extended with the new flag, so a mistaken
  create still cannot destroy a running team. The flag is the explicit "the user asked for a
  separate new team" signal.
- **`agent_teams_status` without `team_id` lists your teams** — `team_id`, name, phase,
  `halted`, `tasks: {total, done}`, `members`, `activeWorkers`, `role` — when there are
  several, and keeps answering a single team in detail.
- **Teams are independent.** Tasks, dependencies, mailboxes, capability attempts and
  archives are read and written per `team_id`; a task id that exists only in another team is
  not reachable, and task ids restart per team. The `ambiguous` failure of the old
  "one team per captain" rule is gone.
- **State-based workspace guards.** A fifth live team is refused
  (`this workspace already has 4 live teams (limit 4); archive one before creating another`)
  and so is a ninth member counted as `working` across all live teams. Both are fuses on the
  live state rather than fixed counts of teams, and archiving frees the slot immediately.
  The configurable keys (per-team worker caps, session caps, a slot summary in `status`)
  arrive with 0.2.0.

## Compatibility

The supported Harness matrix is unchanged: recommended `0.1.5-rc.1`, plus `0.1.2-rc.1`,
`0.1.2-alpha.5`, and `0.1.2-alpha.2`.

`team.json` files written by earlier versions load unchanged — a team created before this
release keeps working, because its existing directory id *is* its `team_id`. Only the
argument surface changed: a call that names no team is no longer resolved from the session,
so an integration that calls a team-scoped tool directly must pass `team_id` (a member of
exactly one team may still omit it). Existing single-team sessions see no difference in
behaviour: `create` returns the same id, the panel shows the same team, and the routes
resolve by id through the captain's team list.

Power users: the tool count is still 18, so no tool allowlist has to be edited.

**Upcoming in 0.2.0:** plan progress and the task checklist, live-team replanning, the
multi-team switcher in the panel (N teams in one session, a per-team and a global worker
cap), and the configurable limit keys.

Update the plugin in your existing profile, then restart Harness:

```sh
dsh plugin --profile <your-profile> add --save-exact @nanmicoder/dsh-agent-teams@0.1.24
```
