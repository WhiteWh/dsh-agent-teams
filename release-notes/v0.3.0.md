# AgentTeams v0.3.0

A contract release on top of 0.2.2, in the owner's round 3: **a phase becomes a unit of
work you can close**, and **the progress bar tells the three stretches of a plan apart**.
It also carries the round-3 panel work — a three-row work plaque, a collapsible phases
section and a member node that is large by default and folds into a tray on demand.

## Phases close, and a closed phase takes no new work

- The captain closes a phase **after accepting its tasks**: one more operation of the
  captain-only replan batch, `{ action: 'close_phase', phase_id: 'E0' }`. It is allowed
  only when every task in the phase is terminal; otherwise it is refused naming the
  phase and the tasks still open (`phase "E1" still has 1 open task(s): t2 (pending) —
  accept and settle them first`). A `failed` task counts as settled — it is evidence of
  a real attempt, and Delivery, not the phase, judges it.
- **A closed phase accepts no new work.** `agent_teams_create_task` with `phase: 'E0'`
  and a replan `add_task`/`move_phase` into it are both refused, and the refusal points
  at the only way forward: declare a new phase (`move_phase`/`add_task` with a new
  `phase_id` and a `title`).
- The state carries `plan.phases[].closed` and `closedAt`; both are optional and
  validated, so a `team.json` written by an earlier version keeps loading with every
  phase open. The snapshot publishes them, the board draws that column's underline in
  the delivered tone with a `Closed` marker, and the running-plan editor lists the phase
  as a disabled option instead of hiding it.
- The captain protocol (rule 7) now states the obligation, and the tool description
  lists the new operation.

## One progress bar in three colours

- The percentage stays one number, but the bar behind it is split into **the original
  plan** (blue), **what the captain added while it ran** (amber) and **what arrived after
  the plan had settled** (green). Each zone is as wide as its stretch is big and fills
  with the share that stretch delivered; the legend under the bar names all three with
  their counts.
- The attribution is recorded on the task when it is created — `origin`: `plan`, `added`
  or `followup` — and never moves, so repairing or reopening the plan cannot reshuffle
  history. A task with no recorded origin counts as plan work. Because the replan tool is
  the captain's (a user never calls it), the moment of creation is what identifies a
  user's later request: work created while the plan still owes something is `added`,
  work created after every original task settled is `followup`.
- `progress.segments` carries the three stretches on the host payload; a panel reading a
  payload without it degrades to one plan-only zone rather than inventing a split.

## Panel work in the same release

- **The work plaque is three dot rows**, not five — the taller plaque was sized for the
  retired two-line member row.
- **The phases section collapses** like the members list and the checklist: a header with
  the column count, the same chevron, open by default.
- **A member node is large by default again** and folds into a compact tray on demand: the
  chevron at the node's right edge folds *that one* member (portrait spanning both lines
  with the action ring, role in words, model badge, state word and the sentence behind it,
  the task chips behind their label) into the one-line tray, and leaves its neighbours
  alone. Fixing this also un-stuck the tray's action symbol, which the base corner-ring
  rule had left floating at the row's right edge.

## Fixes a defect that could freeze the whole web client

- **The chain walk in the phase board is memoised.** The round-2 layout computed a
  task's chain depth by visiting every dependency *path*, and a layered plan multiplies
  paths by the layer width per layer. Measured on this machine: a declared phase of 48
  tasks in 12 layers cost **7.5 s per render**, 56 tasks in 14 layers cost **130 s** — the
  browser tab froze while the panel loaded, which took the owner's web profile down after
  0.2.2 was installed. It is one visit per task now (the same fixtures lay out in
  **0.3–0.7 ms**), with a regression check on exactly that shape.
- **The panel fences itself off.** The shell's additive overlay does not isolate a
  plugin's render exception, so a defect in this panel could unmount the host's tree and
  leave a blank app. `PanelErrorBoundary` now wraps both the activity overlay and the
  conversation card: a fault renders one line naming it, and the conversation keeps
  working.

## Compatibility

State and tool behaviour changed; the two new state fields are optional, so an existing
team keeps loading. Everything else is additive:

- `agent_teams_replan` takes one more action (`close_phase`), and its result prints a
  change line without a task id for it;
- `team.json` may now carry `tasks[].origin` and `plan.phases[].closed`/`closedAt`;
- the snapshot may now carry `progress.segments` and `plan.phases[].closed`;
- no tool was renamed, no status added, no quality gate changed, and the supported
  Harness matrix is unchanged (recommended `0.1.5-rc.1`).

```sh
dsh plugin --profile <your-profile> add --save-exact @nanmicoder/dsh-agent-teams@0.3.0
```

Then restart Harness and refresh the page — a browser that already has the panel open
keeps the old bundle until it reloads.
